# Rich text (`html:`) in xpando

Research notes and decisions for milestone M3. Everything under "What espanso does" was read
from this repository's source (`espanso-config`, `espanso-engine`, `espanso-clipboard`,
`espanso`), not from the upstream docs.

## What espanso does with `html:`

| Question | Answer | Source |
|---|---|---|
| Which field? | `html:` is a string field of a match, next to `replace:` and `markdown:`. If an entry has several, `replace` wins, then `markdown`, then `html`. | `espanso-config/.../loader/yaml/mod.rs` |
| Is the value changed before it is used? | Only `{{variable}}` substitution (a plain text replace of `{{name}}` or `{{name.field}}`). No HTML parsing, no sanitising, no escaping. | `espanso-render/src/renderer/mod.rs` (`VAR_REGEX`) |
| How is it inserted? | The rendered HTML is put on the clipboard (`Clipboard::set_html`) together with a text fallback, then the paste shortcut is sent. The old clipboard is restored afterwards when `restore_clipboard` is on. | `espanso-engine/.../html_inject.rs`, `espanso/.../clipboard_injector.rs` |
| What is the plain-text fallback? | Generated by the engine from the *rendered* HTML with `html2text` (trivial decorator, very wide lines): paragraphs separated by blank lines, `<br>` is a line break, lists become `* item`, link targets are dropped. Nothing to author. | `html_inject.rs` |
| Windows clipboard | `CF_HTML` ("HTML Format", version 0.9 header, the value wrapped in `<html><body><!--StartFragment-->...<!--EndFragment-->`) plus `CF_UNICODETEXT` for the fallback. | `espanso-clipboard/src/win32/mod.rs` |
| macOS / Linux | Pasteboard `public.html` plus string; X11 `text/html` plus text (native or xclip backend). | `cocoa/`, `x11/` |
| Are `force_mode` / `force_clipboard` relevant? | No. The HTML inject request carries no mode: HTML is always pasted through the clipboard. (`force_mode: keys` has no effect on `html:`, and is not needed.) | `espanso-engine/.../action.rs` |
| Cursor hint `$\|$` | Stripped from the rendered body for every format, then the caret is moved back by a character count measured on the *HTML source*, which is wrong once markup is involved. Do not use `$\|$` in rich text. | `cursor_hint.rs` |
| NUL bytes | The value is converted to a C string, so a NUL fails the paste. The sanitiser removes all control characters. | `win32/mod.rs`, `x11/native/mod.rs` |
| Markdown, for comparison | `markdown:` is converted with `pulldown-cmark` and, if the result is a **single paragraph, the `<p>` wrapper is removed** (to avoid a forced line break in many editors, espanso issue 811). `html:` gets no such treatment: it is pasted exactly as written. | `espanso-engine/.../markdown.rs` |

### Consequences for xpando

* The value must be small, predictable HTML that every paste target understands. Targets differ
  widely (Word, Outlook, Gmail, Slack, Teams, browsers, plain-text fields). The fallback means a
  plain-text field still gets readable text.
* A body that is one paragraph is **written without `<p>`** (like espanso does for markdown), so
  it pastes inline instead of adding a paragraph break. Several blocks are written with `<p>`.
* `{{placeholders}}` are substituted verbatim. They are ordinary text for xpando: never escaped,
  never altered, highlighted in the editor. They are fine in text and inside a link address after a
  safe prefix (`https://x.com/{{id}}`). A placeholder as the *whole* address is refused because
  the scheme cannot be checked.
* Variable values are inserted **unescaped**, so a clipboard or shell value containing `<`, `&`
  or markup becomes markup in the pasted HTML. xpando cannot fix this without an engine change
  (candidate upstream patch: HTML-escape variable output when the match is `html:`). It is
  documented here so users know that `{{clipboard}}` in a rich phrase pastes the clipboard as HTML.
* Whitespace collapses like in a browser. Two spaces in a row are saved as one unless they are
  non-breaking spaces (plain-text conversion writes those where needed).
* Images: espanso has a separate `image_path:` kind. An `<img>` inside `html:` is only a link to
  an image: target applications fetch it themselves (Outlook and Gmail do, many others do not,
  and offline it breaks). `data:` URIs would bloat the YAML and are dropped by several targets.
  xpando therefore allows `<img>` with an `http`/`https` source only, with a visible hint in the
  editor, and drops everything else.

Not verified here (needs a human with the apps): the per-application paste matrix (Outlook,
Word, Gmail, Slack, Teams, plain-text fields), and how each treats headings, quotes, `<pre>`,
`<hr>` and remote images. The plan's "Per-app paste testing matrix" item stays open.

## Allowed HTML subset

Written by xpando (and everything the sanitiser keeps when it reads an existing body):

| Element | Notes |
|---|---|
| `p`, `br` | A single paragraph is written without `<p>`. An empty paragraph is `<p><br></p>`. Trailing empty paragraphs and trailing `<br>` are dropped. |
| `strong`, `em`, `u`, `s`, `code` | `b`, `i`, `strike`, `del`, `ins`, `kbd`, `samp`, `tt` are read as these. Written nested in the fixed order link, strong, em, u, s, code. |
| `a[href]` | `href` must start with `http://`, `https://`, `mailto:` or `tel:` (whitespace and control characters inside are removed before checking). Nothing else is kept: no `target`, `rel`, `title`, `name`. |
| `ul`, `ol`, `li` | Nested lists allowed. A list item with one paragraph is written without `<p>`. |
| `h1`, `h2`, `h3` | `h4`-`h6` are read as `h3`. |
| `blockquote` | May contain paragraphs and lists. |
| `pre > code` | Text only, line breaks and indentation kept. |
| `hr` | |
| `img[src, alt, width, height]` | `src` http/https only; `width`/`height` digits only. |

Text is escaped as `&amp;`, `&lt;`, `&gt;`; a no-break space is written `&nbsp;`; other characters
are written as UTF-8. Blocks are separated by a newline so the YAML stays readable.

### What is dropped

* `script`, `style`, `textarea`, `title`, `noscript` (with their content), and `head`, `iframe`,
  `object`, `embed`, `svg`, `math`, `template`, `select`, `option`, `button`, `input`, `video`,
  `audio`, `canvas` (with their content), comments and doctypes.
* **Every attribute not listed above**: `style`, `class`, `id`, `on*` handlers, `target`, ...
  (colours, fonts and sizes are therefore not kept; the editor notes this).
* Links and images with another scheme (`javascript:`, `data:`, `file:`, `vbscript:`, relative
  addresses, a placeholder as the whole address).
* Tables are flattened: each cell becomes a paragraph. Unknown elements are unwrapped (their text
  is kept). Anything beyond 4 MB, and nesting beyond 64 levels, is cut.

The sanitiser is canonical and idempotent: `sanitize(sanitize(x)) == sanitize(x)` (tested on
generated input). Output only ever contains the elements above, so it cannot contain a script,
event handler or `javascript:` link.

## Safety model

1. **Rust is the authority.** The editor (TipTap) only works on its own schema, but whatever
   it sends is run through `xpando_core::htmledit::sanitize_html` before it touches a file. The
   editor and the read-only view are also *loaded* from the sanitised form, and the read-only view
   never uses `dangerouslySetInnerHTML`: it is a non-editable TipTap instance.
2. **No-op saves never rewrite.** `set_html_body` compares the sanitised new body with the sanitised
   current body; if they are equal the file is returned untouched, so merely opening and saving a
   phrase (or the editor re-serialising `${<b>rs</b>}` as `${<strong>rs</strong>}`) changes nothing.
   The UI additionally only sends a body after the user edited it.
3. **Format-preserving, verified writes**, same net as `edit.rs`: only the lines of the body field
   change; the edited file is re-parsed and every other field of the entry, every other entry and
   every top-level key must be identical, or nothing is written. Line endings and the final newline
   are kept. The value is written as a `|-` block scalar (several blocks) or a double-quoted
   scalar with escapes (one line), whichever reads back identically. Layouts the line scanner does
   not recognise (flow lists, `html` and `replace` together, ...) are refused.
4. **Conversions are explicit.** `replace` -> `html`: text is escaped, blank lines become
   paragraphs, single line breaks `<br>`, spaces HTML would collapse become no-break spaces.
   `html` -> `replace`: paragraphs separated by a blank line, lists as `- ` / `1. `, quotes as `> `.
   If anything would be lost (formatting going to plain text; tabs, runs of blank lines or the final
   newline going to HTML) the conversion fails with a message starting `lossy:`; the UI shows what
   is lost and the user confirms before it is retried.

## Where things are

* `xpando-core/src/htmledit.rs`: sanitiser, plain/HTML conversion, `set_html_body`,
  `convert_to_html`, `convert_to_plain`, tests (including a read-only dry run over real files:
  `cargo test -- --ignored real_files`).
* `xpando-app/src-tauri/src/richtext.rs`: `save_rich_phrase`, `create_rich_phrase`,
  `sanitize_html`, `plain_to_html`, `html_to_plain`.
* `xpando-app/src/RichTextEditor.tsx` (TipTap editor, viewer; loaded lazily through
  `RichLazy.tsx`), `RichBodySwitch.tsx` (plain / rich switch), `richtextUtil.ts` (+ tests),
  `richtext.css`.
